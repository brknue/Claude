## Explicit answers to the four review questions

### 1. Remotes and the sell path
The client cannot directly set price, damage, ore identity, sale value or account balance through these remote signatures. DigBlock checks typeof Instance then membership in Mine.info before using Position; a non-mine Instance fails safely. BuyUpgrade accepts only two strings and derives the next item and price on server. getRoot requires a live Humanoid. The mutation blocks do not yield, so no per-request yielding re-entry or duplicate award of the same destroyed block was found in those paths. See DD-04/DD-05 for access/timing bypasses.

Selling uses only server-held inventory and Config prices, clears inventory before the non-yielding coin update, and rate-limits sales. **No arbitrary-coin grant or double sale found by inspection.** However, Touched alone is not proof of authorized proximity under client-owned physics. Before release, validate root-to-pad distance/overlap on the server as well; this is hardening for the sell location, not evidence of fabricated ore value. Review movement trust separately if preventing teleport cheating is required.

Accepted remote work is bounded: dig performs fixed dictionary lookups, scans at most the configured ore types for bag count, and reveals at most six neighbors; upgrades use fixed lists. No payload-driven unbounded loop found. Rejected dig requests run checks before the accepted-hit limiter, so server ingress limiting remains useful against spam. This is not proof against network saturation.

### 2. Persistence
**Session locking/ownership and guarded updates are required before public release under the current whole-profile model.** The smallest safe direction is one validated record per player with schema version, session token/lease and revision, an atomic acquisition/update contract and a serialized per-key save lifecycle. A maintained persistence implementation can be evaluated instead of hand-writing this. UpdateAsync alone does not merge two arbitrary stale whole-profile snapshots.

- Failed load: the loaded flag prevents overwriting stored progress with defaults; **no destructive fallback save found**. DD-03 concerns misleading unsaved gameplay.
- Leave during load: lines 108–110 recheck membership after GetAsync/retries; **no profile installation after an ordinary departure found**.
- Rejoin across servers: DD-01 permits stale overwrite.
- Autosave racing leave/shutdown: DD-01; no single in-flight save/ordering guard.
- Exhausted retries/final departure: DD-02 discards recovery state.
- Shutdown: the explicit deadline is bounded, but is not a persistence success guarantee. Do not claim every pending save completed because BindToClose returned.
- Corrupt/old data: DD-11; there is no schema version or migration policy.

Useful official guidance: [datastore best practices](https://create.roblox.com/docs/cloud-services/data-stores/best-practices) discusses atomic record organization, ordered retries, unknown write outcomes and bounded backoff. In particular, a failed response does not prove the backend did not commit a write.

### 3. Mine grid, regeneration and memory
For integer coordinates inside the guards, key=(y-1)*W*W+(z-1)*W+x is unique across 1..W*W*D. With W=16,D=40, that is 10,240 possible entries. reveal refuses out-of-range coordinates and any non-nil key, preserving false as “already dug.” Destroying a block removes its info entry, marks its key false and examines exactly six axis neighbors. **No grid-key collision or repeat-award bug found by inspection.**

generate sets locked before its first yield, destroys known parts and clears both dictionaries before rebuilding the top layer. Main rejects hits while locked; after rebuilding, old part references have no info. **No unbounded cross-refill table/part growth found by inspection.** Within one refill, grid can grow to the fixed 10,240-cell bound, and rare visible blocks each add a light. Profile the worst case rather than claiming a safe device budget. Unexpected external insertion of unmanaged parts in Blocks is outside the module's cleanup contract.

DD-06 concerns players standing/entering during regeneration. Generation calls are sequential in baseline Main; no second concurrent caller was found. There is no finally-style unlock if generation errors: verify current asset/config validity and decide how the game recovers from a refill exception.

### 4. Client lifecycle, cost and mobile behavior
No accumulating connection loop was found: attribute, prompt, input and Heartbeat handlers are registered once in this StarterPlayerScripts LocalScript, and the GUI has ResetOnSpawn=false. Character references are looked up per call. This conclusion assumes a single copy of the script and normal player-session lifetime. The viewport listener is bound only to the initial CurrentCamera, so replacing the camera can leave scaling stale; cover this in UI work.

On desktop, getTarget performs one raycast and allocates RaycastParams/filter data each Heartbeat even while idle. That is bounded per frame, **not a demonstrated performance failure**. Cache suitable params, reduce HUD writes to actual changes, and profile before adjusting hover frequency. No benchmark was run. DD-07/DD-08/DD-09/DD-10 describe concrete UI/input risks to reproduce.

## Required Studio confirmation: high-priority findings
Use a separate test game/datastore and test-only injectable persistence adapter; do not corrupt real player records. Roblox Studio currently uses one retry attempt in this module, so a single-client Play success does not exercise live three-attempt timing.

### T1 — DD-01: competing sessions
Two independent server contexts operate on one synthetic user key. Server A loads version N and is held. Server B attempts to acquire/load, changes coins/drill and saves. Release A's stale save. Baseline can overwrite B; fixed implementation must block B until safe takeover or reject A's stale owner write. Log owner/revision and final record. Two ordinary different-user clients do not reproduce same-user contention.

### T2 — DD-01: reversed save completion/retry
Start autosave A, hold/fail its first write, mutate a test profile, then trigger leave save B. Make B finish before A's retry. Final record must retain B/newest revision; there must be only the permitted in-flight operation per key. Repeat with BindToClose and release overlapping. Use deterministic injected delays rather than hoping real service latency causes the race.

### T3 — DD-02: exhausted final-save failure
After successful load and earned progress, fail every release-save attempt. Verify an explicit failure result, a retained dirty snapshot with observable retry state, and no false “saved” message. Restore service within the supported recovery window and prove exactly the latest state is stored. Repeat during shutdown with writes pending near the deadline. Document what remains unrecoverable after process termination.
